## 2. Ubuntu 설치 과정

### 2.1 문제 1: 디스크 볼륨 축소 시 여유 공간을 전체 인식하지 못함

**증상**
Windows 디스크 관리에서 파티션 축소를 진행할 때, 실제 여유 공간이 200GB 이상 존재함에도 불구하고 그 일부인 40GB만 축소 가능한 볼륨으로 인식되었다.

**원인**
Windows의 파일 저장 방식 특성상 데이터가 디스크에 빈 공간 없이 순서대로 정렬되어 저장되지 않고, 여러 차례의 파일 생성·삭제·이동 등의 조작을 거치며 사용 가능한 여유 공간이 디스크 전반에 흩어져 존재하게 된다.
Windows 기본 디스크 관리 도구는 파티션의 끝부분에 연속된 여유 공간만 축소 가능한 영역으로 인식하기 때문에, 흩어져 있는 여유 공간 전체를 하나의 축소 가능 영역으로 잡아내지 못한 것이다.

**해결**
Windows 기본 디스크 관리 도구에서는 이렇게 흩어진 공간을 정렬할 수 없다. 대신 외부 파티션 관리 프로그램(프로그램 명: epm_free)을 사용하여 볼륨 정리 및 파티션 축소를 진행하였다. 참고로, 이 방법을 통해 볼륨을 정리하게되면, Windows의 작업 형식과 다르기 때문에, 이후 다시 Windows 디스크 관리 도구로 해당 파티션을 수정하려 할 경우 에러가 발생할 수 있으므로, 이 경우에도 동일하게 외부 프로그램을 사용해야 한다.

### 2.2 문제 2: 제조사·모델별로 상이한 BIOS 설정 방법

**증상**
BIOS 설정 방법이 노트북 제조사 및 모델마다 다르게 설정되어 있어, BIOS 진입 방법이나 메뉴(부팅 우선순위 등) 설정 등이 달라 방법을 몰라 어려움을 겪었었다.

**해결**
사용 중인 노트북 모델(Lenovo IdeaPad Slim3시리즈)을 특정하여 구글링한 결과, 아래와 같은 방법으로 해결하였다.

- **BIOS 진입**: 부팅 시 제조사(Lenovo) 로고가 화면에 표시되는 순간 `F2` 키 입력
- **USB 부팅 설정**:
  1. Boot 메뉴에서 USB Boot 항목을 활성화
  2. UEFI 설정에서 부팅 순서 목록 중 `USB HDD` 항목을 최상단으로 드래그하여 이동(부팅 순서만 방향키 등 조작이 안됨)

위 과정을 통해 USB로 정상적으로 부팅하여 Ubuntu 설치를 진행할 수 있었다.

### 2.3 문제 3: 설치 후 재부팅 시 안내 문구 출력

**증상**
Ubuntu 설치를 완료하고 재부팅하는 과정에서 다음과 같은 문구가 출력되며 부팅이 진행되지 않았다.

```
Please remove the installation medium, then press ENTER
```

**원인 및 해결**
구글링을 통해 확인한 결과, 위 문구는 Ubuntu 설치에 사용한 USB를 컴퓨터에서 제거해야 한다는 의미였다. 연결된 USB 장치를 모두 제거한 후 `Enter` 키를 입력하여 정상적으로 부팅을 완료할 수 있었다.

## 3. Git 실습 내용

실습하기 위한 폴더에 실습용 패키지를 생성하고, 해당 패키지 폴더를 하나의 Git 저장소로 초기화하여 add, commit, diff, branch 기능을 직접 실습해보았고, 아래는 실습 과정을 통해 이해하게 된 각 명령어의 의미와 특성이다.

### 3.1 git init 및 저장소의 범위

Git 저장소는 `git init`을 실행한 폴더를 기준으로 그 하위 경로에만 적용됨.
저장소가 초기화되지 않은 폴더(ros2_ws/src/'실습용 패키지'에서 `src` 폴더)에서 `git add`나 `git commit`을 시도하면 "깃 저장소가 아닙니다"라는 에러가 발생하는데, 이는 Git이 해당 경로 및 상위 경로 어디에도 `.git` 폴더를 찾지 못했기 때문이라고 하며, git을 사용할 때, 상위 폴더인지 하위 폴더인지 유의해야한다고 이해하였다.

### 3.2 add & commit

`git add`는 작업 디렉토리에서 수정하거나 새로 만든 파일 중 다음 커밋에 포함시킬 파일을 선택하여 staging 영역에 올려두는 단계이고, `git commit`은 그렇게 staging된 내용만을 모아 하나의 스냅샷으로 저장소 이력에 기록하는 단계라는 것을 이해하였다. 즉 파일을 수정했다고 자동으로 커밋에 포함되는 것이 아니라, add로 지정한 내용까지만 commit의 대상이 된다는 것으로, 원하는 파일만을 저장하고, 그렇지 않은 파일은 커밋에서 제외시킬 수 있음을 이해하였다.

또한 한 번 add를 했더라도 그 이후 파일 내용을 다시 수정하면, staging된 버전과 현재 작업 디렉토리의 버전이 서로 달라지게 되어 git이 이를 "아직 스테이징되지 않은 변경 사항"으로 별도 표시한다는 것을 확인하였고, 이를 통해 add는 파일 자체를 계속 추적하며 자동으로 갱신해주는 개념이 아니기 때문에 커밋할 때마다 add를 해줘야 한다는 점을 이해하였다.인하는 습관이 중요하다는 것을 체감하였다.

### 3.3 diff

`git diff`는 최근 커밋 시점의 파일 상태와 현재 작업 디렉토리의 파일 상태를 줄 단위로 비교하여, 삭제된 부분과 추가된 부분을 구분해 보여주는 기능임을 이해하였다.
커밋하기 전에 diff로 변경 내용을 미리 검토함으로써, 의도하지 않은 수정이 포함되지는 않았는지 확인할 수 있기 때문에 commit 이전에 크게 도움이 됨을 느꼈다.

`git difftool`은 `git diff`와 동일하게 변경 내용을 비교하지만, vimdiff를 호출하여 좌우 또는 분할 화면으로 더 보기 쉽게 차이를 보여주는 기능이라는 것을 이해하였다. 다만 이 기능은 git 자체에 내장된 것이 아니라 별도의 외부 프로그램의 설치가 필요하지만, 'diff'보다 차이를 비교하기 수월하며, 해당 기능 내에서 수정도 가능함을 실습 과정에서 깨달았다.

### 3.4 branch

`git branch`는 현재까지 저장된 내용에서 이어지는 하나의 분기점을 만드는 기능이라고 이해하였다. branch 기능을 사용하면 새로 작성된 내용이 있더라도, 언제든 기존의 내용으로 되돌릴 수 있고, 새로 작성한 내용이 마음에 들면
해당 내용을 추가할 수 있어 유용하다고 이해하였다. 따라서 이를 이용하여 보존해야 하는 내용에 위험 없이 새로운 내용을 작성할 수 있다고 느꼈다.

`git switch`로 다른 브랜치로 이동하면, 이동한 브랜치의 내용만 표시되며, 이 때, 이전에 작업중이던 브랜치의 내용은 표시되지 않으니 해당 내용을 보기 위해선 다시 브랜치를 이동해야 함을 이해했다.

`git merge`는 다른 브랜치에서 진행한 변경사항을 현재 브랜치로 통합하는 기능이며, 병합 대상 브랜치가 분기 이후 별도의 변경 없이 그대로 있었던 경우에는 새로운 병합 커밋을 만들지 않는다. 또한, 두 브랜치가 같은 파일의 같은 부분을 서로 다르게 수정한 상태에서 merge를 시도하면 git이 자동으로 병합하지 못하고 충돌이 발생하며, 이 경우 해당 파일 안에 두 브랜치의 내용이 특수 기호로 함께 표시되므로 사용자가 직접 원하는 내용으로 정리한 뒤 다시 add와 commit을 거쳐야 병합이 완료된다는 점을 이해하였다.
