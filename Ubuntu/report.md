# Ubuntu 설치 및 Git 실습 보고서

## 1. 개요

본 보고서는 Windows가 설치된 노트북(Lenovo IdeaPad 시리즈)에 Ubuntu를 듀얼 부팅으로 설치하는 과정과, 이후 ROS2 워크스페이스 내 임시 패키지를 활용하여 진행한 Git 실습 내용을 정리한 것이다. 설치 과정에서 발생한 문제와 해결 방법, 그리고 Git 실습 중 발생한 문제와 그 해결 과정을 통해 이해한 Git의 주요 기능(add, commit, diff, branch)에 대한 내용을 포함한다.

---

## 2. Ubuntu 설치 과정

### 2.1 문제 1: 디스크 볼륨 축소 시 여유 공간을 전체 인식하지 못함

**증상**
Windows 디스크 관리에서 파티션 축소를 진행할 때, 실제 여유 공간이 200GB 이상 존재함에도 불구하고 그 일부만 축소 가능한 볼륨으로 인식되었다.

**원인**
Windows의 파일 저장 방식 특성상 데이터가 디스크에 빈 공간 없이 순서대로 정렬되어 저장되지 않고, 여러 차례의 파일 생성·삭제·이동 등의 조작을 거치며 사용 가능한 여유 공간이 디스크 전반에 흩어져 존재하게 된다. Windows 기본 디스크 관리 도구는 파티션의 끝부분에 연속된 여유 공간만 축소 가능한 영역으로 인식하기 때문에, 흩어져 있는 여유 공간 전체를 하나의 축소 가능 영역으로 잡아내지 못했다.

**해결**
Windows 기본 디스크 관리 도구 대신 외부 파티션 관리 프로그램을 사용하여 디스크 조각 모음(볼륨 정리) 및 파티션 축소를 진행하였다. 참고로, 이후 다시 Windows 디스크 관리 도구로 해당 파티션을 수정하려 할 경우 에러가 발생할 수 있으므로, 이 경우에도 동일하게 외부 프로그램을 사용해야 한다.

### 2.2 문제 2: 제조사·모델별로 상이한 BIOS 진입 방법

**증상**
BIOS(UEFI) 설정 화면에 진입하는 방법이 노트북 제조사 및 모델마다 다르게 설정되어 있어, 일반적으로 알려진 방법(F2, Del 등)이 바로 적용되지 않는 경우가 있었다.

**해결**
사용 중인 노트북 모델(Lenovo IdeaPad 시리즈)을 특정하여 구글링한 결과, 아래와 같은 방법으로 해결하였다.

- **BIOS 진입**: 부팅 시 제조사(Lenovo) 로고가 화면에 표시되는 순간 `F2` 키 입력
- **USB 부팅 설정**:
  1. Boot 메뉴에서 USB Boot 항목을 활성화
  2. UEFI 설정에서 부팅 순서 목록 중 `USB HDD` 항목을 최상단으로 드래그하여 이동

위 과정을 통해 USB로 정상적으로 부팅하여 Ubuntu 설치를 진행할 수 있었다.

### 2.3 문제 3: 설치 후 재부팅 시 안내 문구 출력

**증상**
Ubuntu 설치를 완료하고 재부팅하는 과정에서 다음과 같은 문구가 출력되며 부팅이 진행되지 않았다.

```
Please remove the installation medium, then press ENTER
```

**원인 및 해결**
구글링을 통해 확인한 결과, 위 문구는 Ubuntu 설치에 사용한 USB(설치 매체)를 컴퓨터에서 제거해야 한다는 의미였다. 연결된 USB 장치를 모두 제거한 후 `Enter` 키를 입력하여 정상적으로 부팅을 완료할 수 있었다.

## 3. Git 실습 내용

### 3.1 실습 환경 준비

ROS2 워크스페이스(`~/ros2_ws/src`) 내부에 실습용 임시 패키지(`test_git`)를 생성하고, 해당 패키지 폴더 내부에서 Git 저장소를 초기화하여 실습을 진행하였다.

```bash
# 워크스페이스 및 src 폴더 생성
mkdir -p ~/ros2_ws/src
cd ~/ros2_ws/src

# ROS2 패키지 생성
ros2 pkg create test_git --build-type ament_cmake --dependencies rclcpp std_msgs
cd test_git

# git 설치 (미설치 시)
sudo apt update
sudo apt install git -y

# git 초기화 및 사용자 정보 설정
git init
git config --global user.name "minchan"
git config --global user.email "you@example.com"
```

### 3.2 add & commit

**개념**
- `git add`: 작업 디렉토리에서 수정하거나 새로 생성한 파일을 커밋 대상으로 지정(스테이징)하는 명령어
- `git commit`: 스테이징된 변경사항을 저장소의 이력(history)에 하나의 스냅샷으로 기록하는 명령어

**실습 및 문제 해결 과정**

1. `git init`을 실행하지 않은 경로(`ros2_ws/src`)에서 `git add`를 시도하여 "깃 저장소가 아닙니다" 에러가 발생함 → 패키지 폴더(`test_git`) 내부로 이동하여 `git init`을 실행한 뒤 문제 해결.
2. 파일 경로를 잘못 지정하여(`src/test.txt`가 아닌 `test1.txt`) "경로명세가 어떤 파일과도 일치하지 않습니다" 에러 발생 → 실제 파일 위치를 `git status`, `ls`로 확인 후 정확한 경로(`src/test1.txt`)로 재시도하여 해결.
3. `git add` 이후 파일 내용을 추가로 수정하여 스테이징된 버전과 실제 파일 내용이 달라진 상태에서 `git commit`을 시도하자 "커밋하도록 정하지 않은 변경 사항"이 있다는 메시지 출력 → `git add`를 다시 실행하여 최신 상태를 스테이징한 뒤 커밋하여 해결.
4. Git 사용자 정보(`user.name`, `user.email`)가 설정되지 않아 최초 커밋 시 "Author identity unknown" 에러 발생 → `git config --global`로 사용자 정보를 설정한 뒤 정상적으로 커밋 완료.

```bash
git add src/test.txt
git commit -m "메모"
git add src/test1.txt
git commit -m "test1.txt 추가"
```

**이해한 내용**
커밋 전에 반드시 `git status`로 현재 스테이징 상태를 확인하는 습관이 필요하며, add와 commit은 별개의 단계이므로 파일을 수정한 뒤에는 다시 add를 해주어야 최신 내용이 커밋에 반영된다는 점을 이해하였다.

### 3.3 diff

**개념**
`git diff`는 최근 커밋과 현재 작업 디렉토리의 파일 사이의 차이점을 비교하여 보여주는 명령어이다. 커밋 전에 변경 내용을 한 번 더 확인함으로써 실수를 줄이고 확신을 가지고 커밋할 수 있게 해준다.

**실습 결과 예시**

```diff
diff --git a/src/test.txt b/src/test.txt
index 7c4a013..d39cda9 100644
--- a/src/test.txt
+++ b/src/test.txt
@@ -1 +1,2 @@
-aaa
+aaa
+bbb
```

- `-`로 표시된 줄: 이전 버전에 있던 내용
- `+`로 표시된 줄: 새로 추가되거나 변경된 내용

**문제 및 해결**
- diff 결과가 짧아 pager(스크롤 화면)가 열리지 않고 바로 출력되어 종료되는 경우, `j`/`k`/`q` 등의 조작 키를 입력하면 "명령을 찾을 수 없습니다" 에러가 발생한다는 점을 확인하였다. 이는 diff 내용이 화면 크기보다 길어 pager가 열렸을 때만 해당 키 조작이 유효하기 때문임을 이해하였다.
- `git difftool` 최초 실행 시 `diff.tool`이 설정되지 않아 git이 임의로 선택한 도구(`bc`, Beyond Compare)가 미설치되어 있어 에러가 발생함 → `git config --global diff.tool vimdiff` 명령으로 vim 기반 도구를 지정한 뒤 정상적으로 시각화된 비교 화면을 확인할 수 있었다.

```bash
sudo apt install vim -y
git config --global diff.tool vimdiff
git difftool
```

### 3.4 branch

**개념**
`git branch`는 현재 코드 상태의 복사본을 만들어 별도의 작업 흐름으로 관리할 수 있게 해주는 기능이다. 기존 코드를 직접 수정하는 대신 브랜치를 새로 만들어 그 위에서 수정 및 테스트를 진행하고, 문제가 없을 경우에만 원래 브랜치(main/master)에 반영(merge)하는 방식으로 활용한다.

**실습 과정**

```bash
# 브랜치 생성 및 이동
git branch test_27
git switch test_27
git status   # 현재 브랜치 확인

# test_27 브랜치에서 새 파일 작업
echo "test1 content" > src/test1.txt
git add src/test1.txt
git commit -m "branch 커밋 1"

# 커밋 로그 및 브랜치 상태 확인
git log --oneline --all --graph

# 기본 브랜치로 이동
git switch master
ls src/    # test1.txt가 보이지 않는 것을 확인 (브랜치별로 독립된 이력)

# merge 진행
git merge test_27
ls src/    # test1.txt가 master에도 반영된 것을 확인
```

**문제 및 해결**
- 기본 브랜치 이름을 `main`으로 가정하여 `git switch main`을 실행했으나 "잘못된 레퍼런스: main" 에러 발생 → `git branch` 명령으로 확인한 결과 실제 기본 브랜치명이 `master`였음을 확인하고 이름을 바로잡아 해결. (Git 버전 및 설정에 따라 기본 브랜치 이름이 `master` 또는 `main`으로 다를 수 있음을 이해함)
- 브랜치를 전환하기 전, 이전 브랜치에서 커밋하지 않은 수정사항이 남아 있으면 해당 변경사항이 새 브랜치로 그대로 이어진다는 점을 확인함 → `git restore <파일>`로 불필요한 변경사항을 초기화한 뒤 깨끗한 상태에서 실습을 이어갈 수 있었다.

**merge 결과 이해**
```
업데이트 중 9b0b265..783d176
Fast-forward
```
`master` 브랜치가 `test_27`이 분기된 이후 별도의 변경사항 없이 그대로 있었기 때문에, 별도의 병합 커밋 없이 `master`의 포인터가 `test_27`의 최신 커밋 위치로 그대로 이동하는 **Fast-forward** 방식으로 병합되었다.

**충돌(conflict) 개념 이해**
서로 다른 브랜치에서 동일한 파일의 동일한 부분을 다르게 수정한 뒤 merge를 시도하면 충돌이 발생하며, 이 경우 git이 파일 내에 `<<<<<<<`, `=======`, `>>>>>>>` 구분자로 양쪽 브랜치의 내용을 모두 표시해준다. 사용자가 해당 부분을 직접 원하는 내용으로 수정한 뒤 구분자를 제거하고, 다시 `git add` 및 `git commit`을 수행하면 충돌이 해결된다는 점을 이해하였다.

## 4. 종합 정리 및 이해한 내용

| 기능 | 역할 | 사용 이유 |
|---|---|---|
| `git add` | 변경된 파일을 커밋 대상으로 스테이징 | 커밋할 내용을 선별적으로 지정하기 위함 |
| `git commit` | 스테이징된 변경사항을 이력에 기록 | 특정 시점의 코드 상태를 저장하고 이후 되돌리거나 비교할 수 있게 함 |
| `git diff` | 최근 커밋과 현재 파일의 차이 비교 | 커밋 전 변경 내용을 검토하여 실수를 줄이고 확신을 갖고 커밋하기 위함 |
| `git branch` / `git switch` | 독립된 작업 공간(복사본) 생성 및 이동 | 기존 코드에 직접 영향을 주지 않고 수정·테스트 후 반영하기 위함 |
| `git merge` | 서로 다른 브랜치의 변경사항을 통합 | 브랜치에서 검증된 작업 내용을 원래 브랜치에 반영하기 위함 |

이번 실습을 통해 Git의 각 기능이 단순히 개별적으로 존재하는 것이 아니라, **"복사본을 만들어 안전하게 수정 → 변경 내용을 확인 → 이상 없으면 기록 → 필요 시 원래 코드에 통합"**이라는 하나의 작업 흐름 속에서 유기적으로 연결되어 있다는 점을 이해할 수 있었다. 또한 실습 중 발생한 각종 에러(경로 오류, 저장소 미초기화, 사용자 정보 미설정, 브랜치명 혼동 등)를 직접 해결해보면서, 에러 메시지를 정확히 읽고 현재 상태(`git status`, `git log`, `git branch`)를 먼저 확인하는 습관의 중요성을 체감하였다.
